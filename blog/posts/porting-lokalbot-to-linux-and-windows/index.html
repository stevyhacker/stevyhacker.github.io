Porting LokalBot to Linux and Windows with coding agents

Notes from a three-day port of a 150,000-line Swift app to Rust, including a first attempt that didn't work.

Published Oct 20, 2026 AI · Engineering
Back to blog LokalBot for Linux and Windows ↘

On Sunday, October 18, at about six in the morning, I sent a coding agent this message from my phone:

Build a fresh take at implementation of LokalBot for Linux and Windows users with Rust and GPUI, matching the current experience on macOS where it makes sense, but it doesn't have to be completely identical as platforms differ. Build it all in a single PR and add screenshots of both apps running. Use sub agents to speed up and parallelize the work if it helps.

The pull request was merged on Monday afternoon. It had about 150 commits and 148,000 added lines across 365 files. On Tuesday around noon I published LokalBot 0.11.0 with a Windows installer, a portable zip, and .tar.gz, .deb, .rpm and Arch packages for Linux.

I was away from my desk for most of it. On Sunday I sent the session five messages, all from my phone through Claude Code's Remote Control: the prompt, "Resume" twice, "Resuem in 12 30 today" when I ran into my usage limit, and in the evening a request to port four more features. The session itself ran on my Mac. LokalBot's activity log shows the Mac was in use for eleven minutes that day, almost all of it in a chat app.

I don't want to make this sound easier than it was. The agents wrote the code quickly, but that was the part that needed the least from me. The port worked because of the setup around the code: specs written from the Mac app before any Rust, a way for the agents to check a desktop they couldn't see, machines to build on, a few rules for agents sharing those machines, and some decisions I had to make myself. That's mostly what this post is about, along with the first attempt, which didn't work out.

What LokalBot is

LokalBot is a private work memory app for the Mac. It records meetings without a bot joining the call, transcribes them on device, writes notes with a local model, remembers what was on screen, completes text in other apps, and has an agent mode that can work on your files with your approval. The Mac app is about 150,000 lines of Swift.

Almost all of that touches the operating system: system audio capture, reading the focused text field through accessibility APIs, global shortcuts, a tray icon, notifications, launch at login, and screen capture with exclusions. Porting it means answering each of those again for Windows and Linux, and on Linux, Wayland and X11 often need separate answers.

The Windows and Linux version is still an alpha.

The first attempt

This wasn't my first try. On October 2 I asked Codex, in three steps:

  1. "How could we make a version for Linux, Omarchy and Ubuntu and also make a Windows version too, what are my options… also is GPUI worth using"
  2. "Build me just a mock data GPUI/Rust version on this Ubuntu machine… and take screenshots"
  3. "It's pretty good, do a full conversion and open a PR"

By lunchtime I had a working app, about 19,500 lines of Rust with a native GPUI interface and CI on Linux and Windows. I asked a second agent to review the backend, and it found some real bugs. The worst one was about screen history. The app promised to keep it for 14 days, but cleanup only looked at the newest 1,000 moments, so after a few hours of use the promise no longer held. I pasted the review back, and the first agent fixed everything on the list.

Then the PR sat for 16 days, and I closed it.

The review wasn't the reason. The app only looked like LokalBot. It lived in its own folder with its own data model and its own library on disk, so it couldn't open a library recorded on a Mac, and nothing in it would show when it drifted from how the Mac app behaves. In hindsight it went that way because of my second message, where I asked for a mock-data version. The demo became the base for everything that came after.

The second attempt: specs first

The second attempt ran in Claude Code, with a different prompt. I don't think the tool was the difference, since Codex later wrote the port's 24 interface languages and the feature parity audit. What changed was that this attempt spent its first hour on specs instead of Rust.

First, four read-only agents spent 20 minutes reading the Swift code and writing 280 KB of Markdown specs:

  • the library format, SQLite schema and search;
  • the processing pipeline, with every model prompt copied verbatim and every model pinned by URL and SHA-256;
  • the layout, states and exact UI strings of every screen;
  • the CLI and MCP tool schemas, dictation, autocomplete and the privacy rules.

Each spec quoted the Swift it was based on, and the brief told the implementing agents to trust the code when the two disagreed.

Next, before starting any implementers, the lead session wrote the core model types to match the Mac app's JSON field by field. It pointed every agent at a real library that was already in the repo as a test fixture, with meetings, transcripts, chats, a journal and a SQLite database recorded by version 0.10.9 of the Mac app. With tests that load a real Mac library, the port can't move away from the Mac format without a test failing.

Then it wrote a brief for the implementation agents. The brief is 9 KB and reads a lot like onboarding notes for a team of contractors. Each crate has one owner:

Crate Owner
lokalbot-core, lokalbot-cli core agent
lokalbot-ai ai agent
lokalbot-audio, lokalbot-speech speech agent
lokalbot-platform platform agent
lokalbot-engine lead
lokalbot-app lead + two UI agents, split by page

The rules are the kind I'd give people:

  • edit only what you own;
  • commit to your own branch in your own worktree, and don't push;
  • Cargo.lock will conflict, and the lead regenerates it;
  • finish with a report covering the public API others must call, how you tested it, and what's incomplete.

One rule came from my own global instructions: never build on this Mac. Builds and tests ran on a rented OVH server with 16 threads, and Windows builds ran on my gaming PC over SSH. The laptop only edited files.

The part of the brief about the Windows PC had extra rules, because that PC had coin-miner malware with SYSTEM rights until it was cleaned three days earlier:

  • no scheduled tasks, services or startup entries;
  • no changes to security settings;
  • no secrets stored there;
  • nothing installed beyond what a crate needs to build.

Testing without a screen

Writing a tray icon is easy for an agent. Checking that the icon shows up is harder when there's no screen. A lot of the work in this port went into giving the agents ways to see and hear the app on machines without a display.

On Linux, CI starts Xvfb with xfwm4 and an xfce4-panel, runs the release build and takes a screenshot of every page, with the tray next to the clock. The capture script had to learn to wait for the window manager and the tray before taking the screenshots.

To test the live transcript without a microphone, the agent set up a private PipeWire with a virtual mic and virtual speakers and played a scripted two-person conversation into the app's normal capture path. That found two bugs the unit tests hadn't:

  • live sentences were cut off at the newest audio;
  • the player kept a stale length after a recording ended.

GitHub's Windows Server runner has a desktop at 1920×1080 but no mouse, so Windows hides the pointer. The demo recording still shows an arrow, because the script moves a small arrow-shaped window along with the real pointer. Autocomplete is checked in Notepad. The probe types some text, reads the field back, finds the ghost-text window and prints PROBE PASS.

Meetings recorded on the Mac first showed "No recording available" on Linux, because the Mac stores recordings as AAC .m4a and the port wrote WAV. The fix decodes AAC with Symphonia, but decoding wasn't enough by itself. AAC encoders add 2,112 frames of priming silence at the start, and the Mac trims them using the iTunSMPB tag. Without the trim, every transcript timestamp is about 130 ms late at 16 kHz. A test now checks that the fixture's 140-second track comes out at exactly 2,240,000 frames.

The end-to-end runs use real models. Each run starts from an empty library, downloads the default models through the app's own download path, processes a 50-second recording with three speakers, and asks a question about it. On the Ubuntu server, CPU only, processing took 61.5 seconds and the answer with citations 13.5 seconds. On the Windows PC, llama.cpp picked Vulkan on the Radeon GPU, and the answer took 3.4 seconds. These runs caught the model citing its internal source labels ([M1]) instead of moments in the transcript, which a mocked model wouldn't have shown.

One more thing from Sunday. The brief said no scheduled tasks on the Windows PC, but at one point an agent tried to create one anyway. It's the usual way to start a GUI process in a logged-in Windows session from SSH, and on that PC it's also exactly what the malware had done. Claude Code's auto-mode safety check blocked it as unauthorized persistence. The agent moved the interactive Windows checks to GitHub's runners instead and mentioned the refusal in its final report.

Monday: parity work on one shared server

PR 290 had every page but not every feature. On Monday evening I asked Codex to compare the platforms feature by feature, pasted its table into a new session with the line "feature parity is still not there for windows and linux", and asked for a plan.

The plan came back in batches of independent work, with one session and one draft PR for each:

PR Work
304 cloud providers, plus ChatGPT and Claude plan sign-in
305 calendar
306 automatic updates
307 meeting import, merging and boundaries
310 the Ask tool loop

I made a few decisions in the plan:

  • Calendar: a private ICS or CalDAV feed URL on both platforms, plus Evolution Data Server on Linux, and no Outlook or Graph integration.
  • Updates: signed with the existing Sparkle key.
  • Audio: the port keeps WAV, and the Mac app learns to read it.

Then four or five sessions worked on the same 16-thread server at once, and they got in each other's way the way people do on a shared dev box:

  • Cargo target directories. Cargo names workspace crates' build outputs by a hash relative to the workspace root, so two checkouts sharing a target directory overwrite each other's lokalbot-* libraries. The next build then fails with errors like "could not find merge in lokalbot_core" that come from the other checkout's code.
  • pkill. One session's pkill -f "debug/lokalbot --page" killed another session's app twice, with nothing in the log.
  • Displays and sockets. Two sessions on Xvfb display :93 saw each other's windows, and the app's single-instance socket in XDG_RUNTIME_DIR handed one session's launch to another session's running app.

All of that cost the sessions about half an hour. After that, every brief included a rules file: one target directory per checkout, your own display number, your own runtime directory, kill only your own PIDs, and run a renamed copy of the binary so broad pkill patterns can't match it. People sharing a server would sort this out by talking to each other. For the agents, it had to be in the brief.

A few bugs I found interesting

Meanwhile, in another session, Codex added 24 interface languages. Its generator produced one huge nested match, rustc crashed compiling it, and the Linux and Windows release build on master broke. The fix (PR 308) generates sorted tables per locale and adds clippy -D warnings to CI. Since Clippy's invisible_characters lint is deny-by-default, a single zero-width character in a translation would now fail the build, so the generator rejects those up front.

GPUI turns on serde_json's preserve_order feature, and Cargo unifies features across the workspace. So cargo test -p some-crate serializes objects with sorted keys, while cargo test --workspace keeps insertion order, and a test can pass one way and fail the other. My takeaway was to stop asserting on serialized key order and to write wire formats out explicitly.

The self-hosted Windows runner uses local time, UTC+2, while GitHub's runners and the server use UTC. One demo-data test failed only on the PC, and only early in the morning (PR 316).

Windows CI on my PC was also slower than it should have been. The PC has an i5-13400F, with six hyperthreaded performance cores and four efficiency cores. Windows moves long-running work from any process without a foreground window onto the E-cores within about three seconds. That includes the CI runner service and everything started over SSH, so every rustc in a CI job ran on the four slow cores while twelve fast threads sat idle. The obvious fix is the power-throttling opt-out, but child processes don't inherit it. An affinity mask (0xFFF) is inherited. With the mask and two smaller fixes, the Windows job went from 12.5 to 4.5 minutes. The smaller fixes alone got it to 12.1 (PR 323).

On Tuesday morning I asked for Omarchy support ("We should support Omarchy too"). The agent installed Omarchy in a QEMU VM on the server and ran into a few surprises:

  • Hyprland's config and hyprctl dispatch take Lua now.
  • grim hangs in the guest, so screenshots come from QEMU's screendump.
  • Typing through QEMU's control socket runs at half a second per key, so scripts are served over HTTP instead of typed in.
  • The shell locks the session when idle, and then keystrokes go to the lock screen.

CI on my own machines

Hosted Windows CI took about half an hour per run. On Monday night the agents set up GitHub Actions runners on the server and the PC (PR 312):

  • A first job checks which self-hosted runners are idle and sends work there, falling back to GitHub's runners otherwise.
  • Pull requests from forks never run on my machines, and neither do releases or anything with secrets.
  • The runners can't reach my Tailscale network.
  • Windows desktop checks still run on GitHub's runners, never on my PC's desktop.

The median full run went from 32.5 minutes on GitHub's runners to 16.8 on my machines, and to 8.8 after PR 323.

Tuesday: the release

For the release, my part was mostly answering questions:

  • Versioning. I asked whether Windows and Linux should start at 0.1.0. We kept one version for all platforms, 0.11.0.
  • Naming. Alpha, not beta. I had to correct that one.
  • Downloads. Versioned file names.
  • The Windows zip. I asked "what about the windows .zip, is it a .exe or an installer or what?", and it became a per-user installer.

The release job builds six Linux and Windows packages, install-checks the Linux ones in Ubuntu, Fedora and Arch containers, and checks the Windows installer on a Windows runner. Version 0.11.0 was published at 12:22, about 53 hours after the first commit. My last two messages that day were "install it on my ubuntu box and windows box" and "merge it".

How much of this was me

LokalBot keeps a log of my coding-agent sessions and of which app is in front, so I could count:

My messages My time at the Mac
Attempt one, Oct 2 5 can't separate it out, because window titles expire after 7 days. The session ran 09:31–14:02
PR 290, Oct 18–19 6: five from my phone on Sunday, one on Monday 11 minutes on Sunday, almost all of it in a chat app
Parity, CI and release, Oct 19 evening to Oct 20 noon about 30, about 500 words about 2.8 hours

The 2.8 hours is an estimate. It takes my Mac time on each day and credits the port with its share of that day's prompts. Phone time isn't in any of these numbers, and I poked the agents from my phone a lot through Remote Control, mostly with short messages like "Resume" or "merge it".

In total that's about 40 messages and about three hours at the Mac for the second attempt, plus phone time I didn't measure. Most of the messages were one of four kinds:

  • scope: the first prompt, "port the four features", "we should support Omarchy too";
  • unblocking: "Resume", or setting a CI secret myself;
  • decisions: the calendar API, versioning, "alpha", the installer format;
  • release: "merge it".

I didn't review the code myself. I judged the work by the screenshots, the demo videos and the CI runs. I'm only comfortable with that because those checks exercised the app itself: the release build on Linux and Windows desktops, audio through the app's normal capture path, and real models answering from a real library. If they had used mocks, I wouldn't have had much to go on.

There was no API bill. Everything ran on my regular subscription's weekly usage, and I used up nearly all of it two weeks in a row, together with the other projects I was working on at the time. The limit did slow things down. That's what the "Resuem in 12 30 today" message on Sunday was about.

What's not done yet

It's an alpha, and the README has a per-platform table of what works. Some of the gaps:

  • Windows builds aren't code-signed yet.
  • After an in-place update, Installed apps still shows the installer's version.
  • On Wayland, global shortcuts go through compositor bindings, because no global-shortcut API works on every compositor.
  • Accessibility in Qt and Chromium apps is patchier than on the Mac, so autocomplete and screen text work less well there.
  • Agent Mode on Windows has only been tested on a CI desktop, not interactively.
  • The later batches of the parity plan are still open, including coding-agent session history in day memory, voice profiles and more speech models.

What I'd do again

I don't know how well this generalizes, but on this project these things helped:

  • Have agents write specs from the existing code before any new code, with strings, prompts and schemas copied word for word, and pin the data format with real fixtures. Skipping this is what went wrong the first time.
  • Treat parallel agents like a team sharing machines. Give each one its own crate, worktree, branch, target directory, display and process names, and ask each for a written report at the end.
  • Test the app the way a user runs it, with headless desktops, virtual audio devices, CI desktops and end-to-end runs with real models. Those found the bugs that mattered most here, and unit tests found the rest.
  • Decide where builds run. A rented server and a gaming PC did all the builds, the laptop hosted the sessions, and my phone was how I talked to them.
  • Keep the decisions for yourself, like which APIs to depend on and how to name and version a release. A lot of my messages were just "Resume" and "merge it", but the decisions were the ones that mattered.
  • Leave the safety checks on. During the port, one of them stopped an agent from creating a scheduled task on the PC where I'd said not to.

LokalBot for Windows and Linux is on the releases page. The code is in LinuxWindows/, and the original PR, with its screenshots and test results, is #290. It's still an alpha, so bug reports are very welcome.
