Bun 1.3 vs 1.4 on a real production API

I ran both versions side by side on the same server and database. Some routes handled 42% more requests. Others didn’t change at all.

Published Nov 1, 2026Engineering · Performance
Back to blogBizStats ↗

BizStats is a free site for exploring the finances of Montenegrin companies. Its API is a Hono app running on Bun, on one server next to Postgres. This weekend I upgraded it from Bun 1.3.14 to 1.4.4, and I wanted to know what that actually changed.

So I measured it on production, with real request paths from my logs. Here’s the short version:

  • Light routes handled 17–42% more requests per second.
  • Heavier routes that mostly wait on Postgres barely moved, 5% at most.
  • In real traffic, everyday API responses got 8–16% faster.
  • Memory use roughly halved in the test.

I didn’t change any application code to get this.

The upgrade was a few version numbers

I changed the Bun version in package.json, the Dockerfiles and CI. In the API’s Dockerfile, it looks like this:

- FROM oven/bun:1.3-alpine AS runner
+ FROM oven/bun:1.4-alpine AS runner

All 4,082 unit tests, 176 API end-to-end tests and 143 browser tests passed without any changes.

How I tested it

Comparing numbers from different days is unreliable, because traffic changes. So I started two temporary copies of the API on the production server, one on each version. They had the same code, settings and database. They got no public traffic, and their background jobs were off.

Then, for each route, I:

  1. warmed up both copies,
  2. sent requests for 10 seconds at a fixed number of connections (8 for most routes, 4 or 2 for some slower ones), and
  3. repeated that in the order old, new, new, old, so any change in server load hit both versions equally.

Company and person requests cycled through hundreds of real paths from my logs. The logs don’t keep query strings, so I wrote the search, summary and changes requests by hand. That came to 577,467 measured requests, and every one returned status 200.

The server is an 8-core Ryzen 7 9700X that also runs my other projects. I had Claude Code write the small load client, run the test and remove the containers afterwards.

Why some routes gained and others didn’t

Bun can only speed up the part of a request it actually runs. A company profile spends a lot of its time in JavaScript: routing, handling a few quick queries, building the JSON. When that part gets faster, the whole request does. Under this load, its median response time went from 8.9 ms to 6.1 ms.

The site-wide changes feed is the opposite. It runs several database queries and takes about 240 ms under the same load, and very little of that looks like Bun’s work. A faster runtime has almost nothing left to trim.

That’s my reading of the results and of what each route does. I didn’t profile where the time goes.

As for why Bun got faster, the release notes list about eight months of JavaScriptCore updates, with Promises and most string and array builtins moved from JavaScript to C++. I can’t say which of those changes helped my routes most.

What real visitors get

A load test pushes one Bun process as hard as it will go. Real traffic on BizStats is much calmer, about six requests a second that evening, so there’s rarely a queue.

To see that side, I compared the API’s request logs from the two hours before the deploy (44,587 requests) with the first hour after it (20,851). These are medians, so think of them as the typical request:

The log rounds to 0.1 ms, so the fastest routes move in coarse steps. Real requests to the changes feed are cheap, about the 2 ms it takes to ask for one company’s changes. The load test used the site-wide feed, a much heavier query.

Nobody notices a millisecond on a single page. What this buys me is room. The same server can absorb a bigger burst, like a crawler working through thousands of company pages, before requests start to queue. These routes also held their new numbers the next morning, in an hour with about 70% more traffic.

Memory and image size

At the end of the same eight-minute run, the 1.3.14 copy was holding 269 MiB and the 1.4.4 copy 127 MiB, even though it had served more requests. That’s one reading each, and memory moves around with garbage collection, so treat it as a direction rather than an exact figure. It does fit the release notes, which say HTTP servers should use 13–48% less memory.

The live API points the same way: 197 MiB after 14 hours on 1.4.4, against 251 MiB after 4 hours on 1.3.14.

The Docker image also shrank, from 1.33 GB to 1.22 GB. On Alpine, the new install skips the glibc builds of native packages like sharp, which took about 130 MB off node_modules.

What to keep in mind

  • This is one app on one server. How much you gain depends on how much time your routes spend in your database.
  • I compared the official Docker images, and they also moved from Alpine 3.22 to 3.24. So strictly, this is the 1.3 image against the 1.4 image.
  • The load test shared the production database with real visitors. While it ran, the live API’s median went from 2.4 ms to 4.5 ms, and it came back down right after.
  • The traffic comparison covers different hours of the day. I left out routes whose mix of requests clearly changed, like search.

Should you upgrade?

For me it was an easy call. If your API spends most of its time running JavaScript, a few version numbers can buy you a lot of capacity. If it mostly waits on a database, you won’t get much speed from this, and your queries are the better place to look.

Either way, it’s cheap to find out. The whole test took eight minutes to run.
